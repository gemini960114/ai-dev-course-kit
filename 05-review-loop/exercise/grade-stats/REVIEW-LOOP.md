# AI 交叉審查流程（REVIEW-LOOP）

用一個 AI 產出，用另一個 AI 審查，由你自己判斷要不要採納。可以複製這份文件到任何專案中重複使用。

```text
① 產出 → ② 產生審查 prompt → ③ 另一個 AI 審查 → ④ 逐項判斷、只套用同意的
                    ↑______________________________________|
                         重複，直到符合「停止條件」
```

---

## 三個原則

1. **審查者會說錯。** 它可能很有自信地給出錯誤的指令、錯誤的原因，或互相矛盾的建議。每一項都要判斷。
2. **審查者只讀不改。** 審查時不准它執行指令或修改檔案，避免它在你的電腦上做了你不知道的事。
3. **每一輪都留下紀錄。** 保存 prompt、審查原文、你的判斷。

---

## 紀錄方式

```text
你的專案/
├── review-log/
│   ├── round-1-prompt.md     ← 步驟 ② 產生的審查 prompt
│   ├── round-1-review.md     ← 步驟 ③ 審查者的回覆（原文貼上，不要修改）
│   ├── round-1-decision.md   ← 步驟 ④ 你的逐項判斷與理由
│   └── round-2-...
└── （你的程式或文件）
```

git 只需要在**頭尾各 commit 一次**（初版、全部審查完成），每一輪的過程由 `review-log/` 記錄。最後用 `git diff HEAD~1 HEAD` 就能看出初版到完成版改了什麼。

---

## 步驟與提示語範本

### 步驟 ①：產出

對產出用的 AI 說明需求，完成第一版。確認可以執行後，做第一次 commit：

```powershell
git add -A
git commit -m "第 0 輪：初版"
```

### 步驟 ②：請 AI 產生審查 prompt

貼給**產出用的 AI**：

```text
請幫我寫一段給另一位 AI 專家的審查 prompt：說明專案用途、已決定的事，以及 review-log/ 裡前幾輪已修正和已否決的項目，
要求只讀不執行，依 🔴 一定要修／🟡 建議修 回報，沒有重大問題就說「可以發布」。存到 review-log/ 的下一輪 prompt 檔。
```

AI 會存成 `review-log/round-N-prompt.md`。每一輪都用同一段提示語：第 1 輪沒有紀錄，AI 只會寫專案用途；第 2 輪起會自動加上前幾輪已修正與已否決的項目，審查者就不會重複提出。**交出去之前先檢查「已決定的事」**：AI 常把自己寫程式時的設計選擇也列進去，等於叫審查者不要檢查。不是你決定過的，就刪掉或改成「請審查者評估」。

### 步驟 ③：交給另一個 AI 審查

把 prompt 貼給**不同的 AI**（例如產出用 Antigravity IDE，審查用 ChatGPT 網頁版）。審查用的 AI 要和產出用的 AI 使用**不同的模型**，否則容易互相認同。

- 審查者讀不到你的檔案時（例如網頁版），把檔案內容貼在 prompt 最後。
- 把回覆**原文**存成 `review-log/round-N-review.md`。

### 步驟 ④：逐項判斷

貼給**產出用的 AI**：

```text
請逐項判斷以下審查建議（接受／部分接受／否決），附上可驗證的理由，先不要修改：
（貼上審查原文）
```

**你自己看過 AI 的判斷**，有不同意的地方就提出來討論。確定後再說：

```text
只套用同意的項目，修改後實際執行一次，並把判斷存到 review-log/ 的這一輪 decision 檔。
```

AI 會依下方格式存成 `review-log/round-N-decision.md`。

---

## 判斷紀錄格式（round-N-decision.md）

```markdown
# 第 N 輪判斷

審查者：（使用的 AI 工具）

| # | 建議 | 判斷 | 理由（怎麼驗證的） |
| --- | --- | --- | --- |
| 1 | … | ✅ 接受 | … |
| 2 | … | ⚠️ 部分接受 | 問題是對的，但建議的做法會…，改成… |
| 3 | … | ❌ 否決 | 實際執行後發現… |
| 4 | … | 已處理 | 審查者看的是舊版，第 N-1 輪已修正 |

統計：接受 _ 項、部分接受 _ 項、否決 _ 項、已處理 _ 項
```

---

## 怎麼判斷審查建議

| 狀況 | 怎麼做 |
| --- | --- |
| 指出的問題可以重現 | 實際執行一次，確認真的會出錯再改 |
| 給了具體的指令或程式碼 | 不要直接照抄，先想想在你的環境（作業系統、shell、資料）是否成立 |
| 引用版本號、檔案大小、預設值 | 查官方文件確認；查不到就不要寫進去 |
| 兩位審查者意見相反 | 不要多數決，回到事實與你的使用情境判斷 |
| 結論對、理由錯 | 可以接受結論，但在紀錄中寫下正確的理由 |
| 重複提出已否決的事 | 下一輪的 prompt 把它加進「已決定事項」 |
| AI 產生的審查 prompt 裡，「已決定事項」包含你沒決定過的事 | 刪掉或改成「請審查者評估」。第 1 輪通常只有需求文件裡的規定才算已決定 |
| 會讓內容變得很複雜，只為了處理極少見的情況 | 可以改成在文件中提醒，不一定要改程式 |

---

## 停止條件

符合以下全部條件才可以停止：

1. **最後的版本**已交給一個與產出者**不同的 AI 工具**審查，沒有提出未處理的 🔴，並判定「可以發布」。（正式專案建議再請第二個不同的 AI 審查同一版本，兩位都同意才停止。）
2. 所有 🟡 都已有判斷（接受／部分接受／否決）與理由。
3. 套用修改後，已用測試資料**實際執行**過（程式跑過測試資料、安裝流程實際跑過），不是只看審查意見。
4. 如果最後的修改會改變程式行為，修改後的版本要再審查一次；修改前得到的「可以發布」不能算在新版本上。

停止後做第二次 commit：

```powershell
git add -A
git commit -m "審查完成：共 N 輪"
```
